# The runner cap and the coverage gate

Two constraints decide the shape of the job graph in `.github/workflows/deltahdl.yml`, and neither is written anywhere in that file. The repository runs 20 jobs at once and no more, and the lanes behind `assert-coverage` are held back on purpose. A session that reads the file alone will find serialization that looks accidental, measure what removing it would save, and propose a change the user has already declined. Both constraints were stated by the user on 2026-08-06, in the session that rewrote issue #2994.

## Twenty runners at once

Account for the cap before adding a job that starts at the root, widening a matrix, or removing a `needs:` in order to run something sooner. Twenty is what the repository gets, and `deltahdl.yml` already asks for more than that: 32 runner slots want to start at the root, being the 20 shards of `clang-tidy-test`, `build-coverage-lib`, and eleven single jobs. In run 31074983813, when `clang-tidy-test` ran 17 shards and 29 slots wanted the root, peak concurrency was exactly 20 and the jobs that lost the race queued for up to 31 seconds before starting. The 20 shards of `unit-test-coverage` begin as `build-coverage-lib` finishes, so the window they run in fills the cap on its own.

Both matrices went to 20 shards on 2026-08-07 under #2999, and that was the user's decision rather than something the cap argues for. At 17 shards `clang-tidy-test-shard-14` spent 15 seconds of its 81 in `Run clang-tidy` and the rest on installing LLVM, installing ctcache and generating `compile_commands.json`, so three more shards cut about 2 seconds off a shard and add three jobs' worth of that 66-second fixed cost to a root window that was already oversubscribed by nine. Do not propose narrowing them back on the strength of the cap alone.

The consequence is that unblocking a job does not necessarily make the run finish sooner. It moves the job into a window that is already full, and what gets displaced may be on the critical path. `cache-sv-tests` is the worked example: it declares `needs: [unit-test-coverage]`, reads nothing the matrix produces, and runs `git ls-remote` against `chipsalliance/sv-tests` in 3 seconds. Freeing it, and with it `integration-test-coverage` and `e2e-test-coverage`, would save about 45 seconds — in run 31074983813 the last shard ended 224 seconds in, `cache-sv-tests` ran from 226 to 229, and `integration-test-coverage` from 237 to 252. Those two jobs would then want slots during the shard window, a shard would queue in their place, and the shards are what everything downstream waits on. The change was measured on 2026-08-06 and rejected.

## The googletest release is resolved once a run

Take the googletest tag and archive checksum from `cache-googletest` in `.github/workflows/deltahdl.yml`, and do not write a googletest version or checksum into `test/CMakeLists.txt`. The rule the user set on 2026-08-18 is that CI builds against whichever release `google/googletest` has published most recently. `cache-googletest` asks `repos/google/googletest/releases/latest` for that tag on every run, downloads the archive when the cache holds no entry under it, and publishes `outputs.tag` and `outputs.archive-sha256`. The eight jobs that configure the test tree declare `needs: [cache-googletest]` and hand both outputs to `.github/actions/fetch-googletest`, which restores with `fail-on-cache-miss: true`.

Nothing verifies the archive against upstream any more, and that is the cost the rule carries rather than an oversight. `URL_HASH` was removed from `FetchContent_Declare` in `test/CMakeLists.txt` because a checksum cannot be written down for a release that has not been published. The check that remains is narrower: `cache-googletest` measures the SHA256 of the copy it downloaded and the action checks the restored copy against that figure, which catches a cache entry that came back damaged and says nothing about what `github.com` served. A googletest release can also turn the run red with no commit of this repository's behind it.

This reverses #3230, which asked for the same gate and was declined on 2026-08-17 in commit 73733675d. The measurements that decision rested on still hold and are not what changed: the restore hit in all 22 jobs of run 32104113621 and `Fetch googletest` took between 0 and 2 seconds in each, so on a warm cache the gate saves nothing and costs every job behind it the 13 seconds a trivial job such as `assert-no-duplicate-test-names` takes. What the gate buys is the cold run, where run 32057806620 had 14 jobs download the archive at once and 13 of them log `Failed to save: Unable to reserve cache with key googletest-65fab70…, another job may be creating this cache`. Under the always-newest rule a cold run arrives with every googletest release rather than with a deliberate edit, which is the premise that moved.

The gate does not cost a root slot on balance. `build-coverage-lib`, `clang-tidy-src` and the 20 shards of `clang-tidy-test` started at the root before it and now wait behind it, so the root window asks for 22 fewer slots than the 32 recorded above and the run gains one job on its critical path instead.

## A gate over a tree goes in the workflow that watches that tree

Put a check that reads `src/` into `.github/workflows/deltahdl.yml`, and do not widen the `paths:` list of `.github/workflows/scripts.yml` to reach it. A workflow's `paths:` starts the whole workflow rather than the one job that reads the tree, so adding `src/**` to `scripts.yml` would run all 30 of its jobs on every `src/`-only push, 23 of them wanting a slot in the root window that `deltahdl.yml` already oversubscribes by twelve on the same push. `assert-subclause-citations` moved for this reason under #3156, having run in `scripts.yml` where no `src/`-only push started it. Being written in Python is not what decides which workflow a check belongs to; the tree it reads is. Its unit tests stay beside the other Python tests in `scripts.yml`, and `deltahdl.yml` watches `scripts/assert_subclause_citations/**` so that a change to the check itself is still run against `src/`.

## The lanes behind assert-coverage stay gated

Leave the `needs: [assert-coverage]` on `build-asan-ubsan`, `build-tsan`, `build-macos-26-arm64-clang`, `build-ubuntu-24-04-x86-64-clang`, `build-ubuntu-24-04-x86-64-gcc` and `release`. Twenty runners is not enough to run those lanes beside the coverage lane, and running another platform's unit tests before the coverage number is known spends the cap on a result that may be thrown away.

Know what the gate does in practice, because it is not what its shape suggests. `e2e-test-coverage` and `assert-coverage` both carry `if: needs.integration-test-coverage.result == 'success'`, and `integration-test-coverage` runs `run_sv_tests`, which exits 1 while any sv-tests case fails. sv-tests stood at 685 of 830 on 2026-08-17, and at 704 of 830 on 2026-08-06. Read the count off the newest run's `Run sv-tests` step rather than from here, because it moves with every push and a figure written down goes stale without anything signalling it. `assert-coverage` therefore does not run, the threshold in its `Enforce 100% coverage` step is never evaluated, the lanes behind it are skipped on every push, and the last GitHub Pages deployment of the coverage report was on 2026-02-10. The rule in force is "hold the lanes until sv-tests passes", not "hold the lanes until coverage is 100%". This was put to the user on 2026-08-06 and accepted as it stands.

The ordering is not the part that could be loosened. Coverage is measured across all three tiers, so `assert-coverage` merges `profdata-unit-shard-*`, `profraw-integration` and `profraw-e2e` into one profile and would report short of 100% if a tier had not run. Only the hard `== 'success'` condition is a choice, and it is one the user has made.
