# Lead with what it is for

Open with a plain sentence saying what the thing is and what it does, and put the identifiers after that sentence. This holds in an issue body, a commit message, a docstring, a comment in a source file and these notes, wherever the reader asked no question. It does not hold in a reply to a question, which leads with the answer instead. Assume the reader has not opened the files and will not open them while reading.

A name written before that sentence is a demand rather than a service. Telling a reader that `lib/python/lrm/__init__.py` walks a `pypdf` outline into `load_toc`, and that `test/lib/python/lrm/unit/` covers it under a 100% gate, tells them nothing yet, because they do not know what either is for. Say that first: `~/LRM.pdf` decides what deltahdl has to do, the standard cites a rule by its printed subclause number, and nothing in the file turns that number into the pages carrying it. Something therefore has to map a subclause to its page range before a script can read the rule. Then name the module that maps it, the library it reads the outline with and the job that covers it. The names are owed either way, and the order decides whether the reader can use them.

Say what it costs, in ordinary words, near the top. "Every unit test passed, and those passes could not be told apart from real ones" is what a reader needs before they can care that two elaborator paths computed a storage offset where a declared index was required. It belongs in the first few lines rather than in the seventh paragraph. In an issue this is what "Problem" opens with: what the code is there to do, then what is wrong with it, then what the defect costs.

Then cut. A detail earns its place by changing what somebody would do, and it moves later or goes when it does not. `wire [8:1] w` and the two elaborator paths that mishandled it are worth writing where somebody is about to edit those paths, and worth leaving out where somebody is working out why a full suite of passing tests proved nothing. Cutting a correct detail is not vagueness. Replacing it with a coined noun is, and that failure has its own note.

[write-the-exact-name](write-the-exact-name.md) pushes one way only. It was written on 2026-08-02 in `10U-Labs/wan-graph-synthesizer` after two drafts of one issue were rejected for naming nothing, so the correction it records is entirely about adding names. Nothing in it asks what to leave out, or what has to be said before the first identifier appears. This note was written the same day, after the user asked for that issue in simple English: the reply that answered them said the same things in a different order and left three correct details out, and nothing in it had been newly discovered. The issue was ordered for the writer, who knew the shape of the defect before writing a word. The reply was ordered for the reader, who did not.

The "Prose" section of `.claude/CLAUDE.md` states the neighbouring rule, which orders an instruction against the argument for it. This note orders a purpose against a name, which that rule does not cover. Neither settles how long the result may be, and on 2026-08-06 the opening sentence this note asks for, written once per paragraph and with no length against it, was what made three replies unreadable. Nothing enforces any of it, so a green `Documentation` run is not agreement.
